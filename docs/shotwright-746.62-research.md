# shotwright-746.62 — CI artifact upload controls research

- **Date:** 2026-10-29
- **Phase:** R
- **Scope:** reusable workflow policy, consumer guidance, and a browser-view experiment; no workflow edits in this phase.
- **Kickoff:** The task specifies the event split and the existing consumer's two-day choice. No additional owner preference was supplied.

## Context and current state

The project promises review artifacts rather than assertion gates, with artifacts-only CI by default (`docs/design.md:30-37`). The run directory is the publication unit: the reporter generates a gallery even for a failed test result, publishes a manifest atomically, and moves `latest` only after a fully passed run with sound publication (`src/reporter.ts:147-193`, `src/runs.ts:116-130`). The gallery is a self-contained file by design (`docs/adr/0005-gallery-single-file-inline-originals.md:6-22`, `src/gallery/generate.ts:22-32`).

The reusable workflow has nine inputs already, including `retention-days: 7` and `artifact-name` (`.github/workflows/shotwright.yml:5-41`). It runs the consumer's installed `shotwright` through npm/pnpm/yarn, or `scripts/ci/shots.sh` in self mode (`.github/workflows/shotwright.yml:168-177`); the consumer path does not use `npx`. It resolves the current invocation's run-directory file under `!cancelled()`, then uploads that **whole directory** as one default zipped artifact when the path exists (`.github/workflows/shotwright.yml:179-202`). The artifact is named by `artifact-name` or `shotwright-{workflow}-{run_id}-{run_attempt}` and retains for seven days unless overridden (`.github/workflows/shotwright.yml:34-41,194-202`). The path includes the gallery, manifest, screenshots, videos, failure context, data and optional traces when produced; the template warns about their sensitive content (`templates/github/shotwright.yml:23-29`). The job summary links the artifact only after a successful upload (`.github/workflows/shotwright.yml:203-209`). `!cancelled()` means an ordinary failed run can still upload, provided the run-directory file exists; a failure before directory creation cannot produce an artifact (`.github/workflows/shotwright.yml:179-202`).

The template triggers on both `pull_request` and `workflow_dispatch`, passes `mode: consumer`, and leaves retention and upload policy implicit (`templates/github/shotwright.yml:3-5,10-30`). The demo triggers on every push, calls the same workflow with `mode: self`, and currently inherits the seven-day upload (`.github/workflows/demo-shots.yml:3-14`). The README says that CI uploads the current run, including failed evidence, and lists `retention-days` but no upload control (`README.md:308-320`).

**Premise check:** The bead's seven-day, unconditional-upload description still matches the workflow (`.github/workflows/shotwright.yml:34-37,194-202`). ADR 0007's historical “two-input surface” does **not** describe today's code: `runs-on`, `working-directory`, `package-manager`, `playwright-args`, `traces`, `retention-days`, and `artifact-name` have since been added (`docs/adr/0007-ci-reusable-workflow-same-owner-private.md:42-44,73-77`; `.github/workflows/shotwright.yml:14-41`). Its bar for new permanent inputs remains applicable.

## External findings (all links read 2026-10-29)

- GitHub's [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions) says private repositories have a shared artifact/Packages storage allowance of 500 MB on Free or 1 GB on Pro, and measures usage hourly in binary GB-hours. Deletion prevents future accrual, not charges already accrued. The [plan allowance table](https://docs.github.com/en/billing/reference/product-usage-included) corroborates the amounts. The bead's consumer observation is about **120 MB per run, about 69 MB of it gallery**, not a fresh measurement here (`docs/shotwright-746.64-research.md:31-37`). Actual uploaded compressed size and billing impact still need measurement.
- The current [upload-artifact README](https://github.com/actions/upload-artifact) documents `retention-days`, `if-no-files-found`, `archive: false`, one-file-only direct upload, an ignored `name` for direct uploads, a 500-artifact-per-job limit, and logged-in access to `artifact-url`. The [v7.0.0 release](https://github.com/actions/upload-artifact/releases/tag/v7.0.0) confirms that a direct upload fails if the path resolves to multiple files. The [v7.0.2 release](https://github.com/actions/upload-artifact/releases/tag/v7.0.2) matches the action version pinned in this repo (`.github/workflows/shotwright.yml:194-202`); no action upgrade is needed for an experiment.
- GitHub's [2026-02-26 changelog](https://github.blog/changelog/2026-02-26-github-actions-now-supports-uploading-and-downloading-non-zipped-artifacts/) says a single unzipped file may open directly in desktop and mobile browsers, with simple HTML named as an example. It does **not** specify a maximum browser-preview file size, content-type allowlist, response CSP, iframe sandbox, or inline-script behavior. The action README also does not establish those browser guarantees. Treat all five as **unverified**, especially at 69 MB; do not claim that phone review already works. GitHub's [v7 release](https://github.com/actions/upload-artifact/releases/tag/v7.0.0) establishes a one-file cardinality limit, so `archive: false` cannot apply to the whole run directory. A separate `gallery.html` direct artifact can coexist with the zipped run artifact but duplicates gallery bytes in storage.
- Comparable upstream patterns are selective rather than unconditional: [Apache Fineract's reusable integration workflow](https://github.com/apache/fineract/blob/develop/.github/workflows/run-integration-test-sequentially-postgresql.yml) exposes `upload_artifacts: false` and uploads reports when `failure() || inputs.upload_artifacts`, with five-day retention. That is direct precedent for a failure default plus opt-in green-run upload. [Vitest's CI report guide](https://vitest.dev/guide/ui.html#view-reports-from-ci) documents a separate single-file `archive: false` HTML report. Neither proves this gallery works under GitHub's preview policy. GitHub's [contexts reference](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts) says the reusable workflow receives caller inputs and event context, so the caller template can select PR and manual policies.

## Options

| Option | Upload policy | Storage and review trade-off |
|---|---|---|
| **A — recommended** | One `upload` string input: `always`, `on-failure`, `never`; default `on-failure`. Template passes `always` for `workflow_dispatch`, `on-failure` for `pull_request`. Two-day retention default. | Routine green PRs use no artifact storage; manual runs remain reviewable; failed runs retain evidence. Changes the old default for callers that upgrade their workflow tag without supplying the input. |
| B | Default `always`, template selects `on-failure` on PR only; two-day retention. | Existing unmodified callers keep green-run artifacts, but a newly written consumer caller can still silently store every PR run. |
| C | Default `never`, manual runs opt in. | Minimal storage, but failed PR evidence disappears unless every caller remembers to opt in; weakens the artifacts-only CI contract. |
| D | Keep one upload policy and only shorten retention. | Smallest API; it cannot prevent frequent green PR uploads from accumulating. |

## Recommendation

Choose **A**. `upload` is the minimum new permanent input that a real consumer needs: the existing two-day override reduces duration but cannot prevent green PR uploads (`.github/workflows/shotwright.yml:34-37,194-202`). This clears ADR 0007's requirement for a concrete reachable use, despite its permanent copied API cost (`docs/adr/0007-ci-reusable-workflow-same-owner-private.md:24-26,73-77`). Values are exact strings; reject unknown values with a clear error before the shot run. Define `on-failure` as **the shot execution step failed and an invocation run directory was created**, including gallery publication failures. Keep `!cancelled()` so cancellation does not upload; `never` still executes shots and reports their status. Resolve the run directory and upload only when the selected policy needs it. For a failed Playwright run, the reporter attempts gallery generation before manifest publication (`src/reporter.ts:160-181`); upload that directory after failure using the existing `!cancelled()` path (`.github/workflows/shotwright.yml:179-202`). If gallery generation itself fails, upload the manifest and remaining failure evidence; do not promise a gallery that was not published (`src/reporter.ts:175-186`). A setup failure with no directory has nothing to upload.

Set `retention-days` default to **2** for all uploaded modes, matching the real consumer's chosen override recorded in the bead and cutting lifetime versus the current seven days (`.github/workflows/shotwright.yml:34-37`). Do not automatically inspect `github.event_name` inside the reusable workflow: the template should state the event policy explicitly, while callers with other triggers can choose deliberately. The template expression can pass `${{ github.event_name == 'workflow_dispatch' && 'always' || 'on-failure' }}`; the reusable default covers callers that omit it. The demo's `mode: self` should explicitly pass `upload: always` if its green push artifact is still required during this bead; deciding to stop every-push uploads belongs to `shotwright-746.63` (`.github/workflows/demo-shots.yml:3-14`).

Keep the run-directory zip as the primary artifact. Do **not** add a second gallery artifact by default: it adds storage, and direct viewing is unverified. The orchestrator can temporarily add a second upload step on a pushed branch, with `path: <resolved-run-dir>/gallery.html`, `archive: false`, `if-no-files-found: error`, and a distinct step ID. Because direct upload ignores `name`, the artifact will be `gallery.html`; the summary should link each artifact separately. Test a small self-contained control HTML and a real gallery (current about 69 MB, plus a smaller gallery after `746.57` if available). On desktop and mobile, record artifact URL, rendered versus downloaded result, inline-script interaction (filters/lightbox), image load, MIME/Content-Disposition/CSP response headers, console CSP errors, load time, and exact size. Verify that the original zipped run still downloads and that the second upload's storage cost is acceptable. A pushed run is required; local YAML cannot establish GitHub's browser behavior. If script execution or size fails, keep the second artifact out of the implementation and preserve ADR 0025's off-GitHub trigger (`docs/adr/0025-off-github-run-storage-is-an-opt-in-s3-compatible-publish.md:39-45`).

Implementation verification should exercise a green and a failed shot execution for each `upload` value: `always` produces an artifact in both cases; `on-failure` only after the failed run; `never` in neither. In the failed `on-failure` case, inspect the downloaded archive for `gallery.html` and `manifest.json`, and verify that the job stays failed. Also cover cancellation, no-directory setup failure, invalid input, the template's PR/manual selections, two-day default and explicit retention override. Static workflow tests can pin expression wiring; at least one recorded pushed Actions run should verify GitHub's step behavior. This follows the existing workflow test's failed-run check (`test/unit/init.test.ts:888-889`).

Template comment should say that private repositories share their owner's 500 MB Free / 1 GB Pro Actions artifact and Packages allowance; artifacts accrue storage by GB-hour; PRs default to uploading failed runs only, manual runs upload always; `upload` and `retention-days` can be overridden; artifacts live on GitHub, require repository access, and expire. It should remind users that traces and authenticated captures may expose data (`templates/github/shotwright.yml:23-29`). The README CI section needs a concise link to GitHub's [Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions), the three modes, the event defaults, the two-day retention, and the fact that `never` removes the GitHub artifact, without a broad rewrite (`README.md:308-320`; README overhaul is a separate bead).

## Redteam and owner decision (2026-10-29)

A redteam returned "proceed with changes". Adopted:

1. **The reusable default stays `always` with 7-day retention** (owner decision). Changing it would silently drop passing-run artifacts for existing callers on upgrade, and the template sets the mode explicitly, so a new default gains nothing for generated callers. The template sets `on-failure` and `retention-days: 2` for pull requests and `always` for manual dispatch. `docs/design.md` and the README CI section describe the difference.
2. **Incomplete directories.** If manifest publication fails, the reporter removes `manifest.json` and `gallery.html` (`src/reporter.ts:180`). Such a directory is uploaded as diagnostic evidence and labelled incomplete in the job summary, never described as a reviewable run.
3. **`on-failure` follows the shot step.** Give `Run shotwright` an id and upload when its outcome is failure, the run is not cancelled, and a directory resolved. A bare `failure()` would also fire on setup failures.
4. **Declined for this bead:** a production `archive: false` gallery artifact. It duplicates gallery storage and its filename-based artifact name collides when a job calls the workflow twice. It stays a pushed-branch experiment only.
