# External grounding for E10 consumer adoption

Read 2026-10-22. Scope: upstream behavior and comparable products only. The consumer reproduction and shotwright design are in the sibling brief and design document. A quoted fragment beside each link is the supporting upstream text; recommendations are explicitly my inferences. Current stable `@playwright/test` is **1.64.1**, rather than the brief's 1.64.0: npm labels it “latest” ([npm, read 2026-10-22](https://www.npmjs.com/package/%40playwright/test?activeTab=versions)). This is a patch release within the requested 1.64 line.

## A. Playwright 1.64: G1, G2, G3, G4, G9, G13

- **G1 config.** `TestConfig` is the source config shape; resolved reporter input is `FullConfig`. Current documented top-level keys include `globalSetup`, `globalTeardown`, `fullyParallel`, `workers`, `timeout`, `expect`, `reporter`, `testMatch`, `testIgnore`, `metadata`, `preserveOutput`, `outputDir`, `projects`, `webServer`, `retries`, `forbidOnly`, and newer `retryStrategy`. Quote: “This type describes format of the configuration file” and “Controls when failed tests are retried” ([TestConfig, read 2026-10-22](https://playwright.dev/docs/api/class-testconfig)). A closed playwright-bdd design issue explicitly calls mixed full-config options messy because “some fields are conflicting”; its current docs return only a generated `testDir` and put “other playwright options” in Playwright's `defineConfig` ([issue](https://github.com/vitalets/playwright-bdd/issues/169), [docs](https://github.com/vitalets/playwright-bdd/blob/main/docs/configuration/index.md), read 2026-10-22). Serenity/JS instead keeps Playwright's config and adds fixture typing and a reporter: “keep your existing settings” ([Serenity guide, read 2026-10-22](https://serenity-js.org/getting-started/playwright/)). Playwright CT wrappers are no longer a current precedent: “experimental ... packages have been removed” ([component guide, read 2026-10-22](https://playwright.dev/docs/test-components)). Nothing found in these examples that specifically endorses `Omit<PlaywrightTestConfig, HarnessOwnedKeys>`; that would be shotwright's own type design.
- **G2 order.** Default behavior is “Tests in a single file are run in order”; `fullyParallel: true` opts into concurrency within files ([TestConfig, read 2026-10-22](https://playwright.dev/docs/api/class-testconfig)). `test.describe.configure({ mode: 'serial' })` skips subsequent tests after a failure and retries all together: “All tests in the group are retried together” ([Retries, read 2026-10-22](https://playwright.dev/docs/test-retries)). Thus serial mode can repeat staging writes and cleanup on retry.
- **G3 reporter.** `onTestEnd(test, result)` receives a complete result; `onEnd(FullResult)` receives run `status`: `passed`, `failed`, `timedout`, `interrupted`. The reporter may override the run status and exit code. Quote: “TestResult is complete” ([Reporter, read 2026-10-22](https://playwright.dev/docs/api/class-reporter)). `TestResult` exposes `status` (`passed`, `failed`, `timedOut`, `skipped`, `interrupted`), `error`, `errors`, `duration`, `retry`, and `attachments` with `name`, `contentType`, optional `path` or `body` ([TestResult, read 2026-10-22](https://playwright.dev/docs/api/class-testresult): “First error ... equal to the first element”). `TestCase.id` derives from file, title, and project and is “unique within Playwright session” ([TestCase, read 2026-10-22](https://playwright.dev/docs/api/class-testcase)); cross-run persistence is **not guaranteed by that wording**. A stable shotwright identity should therefore retain spec/title/project alongside this link key.
- **G4 failed evidence.** Current source writes `error-context.md` only if there are test errors *and* `buildErrorContext` returns content, attaches it as `name: 'error-context'`, `contentType: 'text/markdown'` ([Playwright source, read 2026-10-22](https://github.com/microsoft/playwright/blob/main/packages/playwright/src/index.ts): “if (errorContextContent)”). `outputDir` is “cleaned at the start”; `preserveOutput` defaults to `always` and only determines retention *within a run*, with `never` and `failures-only` alternatives ([TestConfig, read 2026-10-22](https://playwright.dev/docs/api/class-testconfig)). Nothing found in TestConfig to disable initial cleaning. This is distinct from shotwright's end-of-run deletion. A recent issue confirms `preserveOutput` “controls retention, not generation” ([Playwright issue 43063, read 2026-10-22](https://github.com/microsoft/playwright/issues/43063)).
- **G9 trace.** Trace docs say tracing captures “browser operations and network activity”; the viewer exposes request and response headers and bodies ([Tracing](https://playwright.dev/docs/api/class-tracing), [Trace Viewer](https://playwright.dev/docs/trace-viewer), read 2026-10-22: “request body and response body”). An open redaction issue was **nothing found** in the targeted trace-issue search. Related issues do show plain-text password in reports and authentication headers in failure logs ([issue 36800](https://github.com/microsoft/playwright/issues/36800): “password in plain text”; [issue 31717](https://github.com/microsoft/playwright/issues/31717): “Authorization: ApiKey 1234”, read 2026-10-22). A trace redaction option was **nothing found** in the current tracing API.
- **G13 capture/names.** `page.screenshot({ fullPage })` defaults to `false`: “instead of the currently visible viewport. Defaults to `false`” ([Page, read 2026-10-22](https://playwright.dev/docs/api/class-page)). `TestCase.id` still documents its file/title/project derivation; a guarantee for a human-readable test-title slug in Playwright attachment filenames was **nothing found** ([TestCase, read 2026-10-22](https://playwright.dev/docs/api/class-testcase)).

**What this means for shotwright.** Preserve caller config except explicitly owned keys, and document those exclusions; default file-local ordering. Persist run and attempt outcomes from reporter events, but use shotwright's spec/title identity for cross-run pairing. Copy failure attachments before removing `.pw`, and document the full-page default and trace disclosure.

**Decoder/weight.** Pixelmatch takes decoded RGBA data; its CLI uses `pngjs` (`import {PNG} from 'pngjs'`) ([CLI, read 2026-10-22](https://github.com/mapbox/pixelmatch/blob/main/bin/pixelmatch)). `pngjs` is pure JavaScript with a sync PNG read/write API ([npm README, read 2026-10-22](https://www.npmjs.com/package/pngjs?activeTab=versions): “PNG.sync.read(buffer)”). `sharp` is a Node-API/libvips image-processing dependency supporting more formats and prebuilt binaries; quote: “high speed Node-API module” ([npm, read 2026-10-22](https://www.npmjs.com/package/sharp)). Its install footprint is therefore materially heavier than a PNG-only decoder, an inference from the native binary requirement. `looks-same` currently has five npm dependencies ([npm, read 2026-10-22](https://www.npmjs.com/package/looks-same?activeTab=versions): “5 Dependencies”).

**What this means for shotwright.** The mature tools show a per-pair changed result and visual diff, even when approval is separate. Use a deterministic equal-size PNG comparison and report dimensional mismatch separately. Treat thresholds as detection settings, not correctness claims. Keep comparison exit zero by default and offer `--fail-on-change` for the parity consumer.

## C. Reusable GitHub Actions workflow and G10

- `jobs.<id>.runs-on` accepts a string, array of labels, or `group`/`labels` map. The contexts table allows `inputs` there; `fromJSON` turns a JSON array string into an array. Quote: “An array of strings” ([syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [contexts](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts), [expressions](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions), read 2026-10-22). The JSON-array-input use is an inference from those three documented rules, not a copied canonical example.
- Workflow-level `defaults.run` disallows expressions, but the contexts reference allows `inputs` in **job-level** `jobs.<id>.defaults.run`; the syntax also says that job-level `working-directory` “can reference several contexts” ([syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [contexts](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts), read 2026-10-22). Place `${{ inputs.working-directory }}` at job level, or on individual run steps.
- A reusable-workflow call supports `with` and `secrets`, not caller `env`; caller workflow `env` “are not propagated” ([reusable limits, read 2026-10-22](https://docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations)). Pass public values through declared inputs or repository `vars`; pass credentials through explicit declared secrets or `secrets: inherit` (same organization/enterprise), then map both to the called job's `env` ([reuse docs, read 2026-10-22](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows): “use the `inherit` keyword”).
- Current `actions/upload-artifact` README uses **v7**, with `if-no-files-found: warn|error|ignore`; `retention-days` minimum 1, maximum normally 90, 0 means repository default ([README](https://github.com/actions/upload-artifact), [releases](https://github.com/actions/upload-artifact/releases), read 2026-10-22: “uses: actions/upload-artifact@v7”). The repo settings may lower the maximum. GitHub says `always()` can resist cancellation; it recommends `!cancelled()` when failed jobs should still upload but cancellation should work ([cancellation guide, read 2026-10-22](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation): “if: always() would evaluate to true”).
- A current reusable workflow with a `package-manager` input and lockfile autodetection was **nothing found** in targeted GitHub search. A documented independent detector uses lockfiles, then `packageManager`, then `devEngines.packageManager`, searching parent directories ([package-manager-detector, read 2026-10-22](https://github.com/antfu-collective/package-manager-detector/): “By default ... searches ... lock files”).

**What this means for shotwright.** The workflow can accept runner labels, job-level workdir, manager, Node version, output path, arguments, and retention as inputs. Use `!cancelled()` to publish a failed run; choose `if-no-files-found: error` once a run path is expected. The generated caller must explicitly pass application inputs and secrets, since a blanket `env` handoff is unavailable.

## D. Package-manager detection and G11

- npm's default user-agent pattern is `npm/{version} node/{version} {platform} {arch} workspaces/{bool}` ([npm config, read 2026-10-22](https://docs.npmjs.com/cli/using-npm/config/): “Default: `npm/{npm-version} node/{node-version}`”). Example observed leading tokens: `pnpm/8.6.3 npm/? node/v16.17.1` ([pnpm issue 6701, read 2026-10-22](https://github.com/pnpm/pnpm/issues/6701): “pnpm/8.6.3 npm/?”); `yarn/1.7.0 npm/?` ([Yarn Classic issue, read 2026-10-22](https://github.com/yarnpkg/yarn/issues/6004): “npm_config_user_agent”); Bun example `bun/0.6.0 npm/?` ([Bun issue, read 2026-10-22](https://github.com/oven-sh/bun/issues/2793): “bun/0.6.0 npm/?”). Yarn Berry's changelog says its `npm_config_user_agent` includes a `node` field, but an exact present-day full Berry string was **nothing found** ([changelog, read 2026-10-22](https://github.com/yarnpkg/berry/blob/master/CHANGELOG.md): “node field ... leading v”). These examples establish a leading `manager/version` token, not a permanent full-string schema.
- `which-pm-runs` keys on `npm_config_user_agent` ([npm, read 2026-10-22](https://www.npmjs.com/package/which-pm-runs): “any other package manager that sets” it). `preferred-pm` uses lockfile clues such as `package-lock.json` ([npm, read 2026-10-22](https://www.npmjs.com/package/preferred-pm?activeTab=code): “npm is preferred”). `package-manager-detector` explicitly uses lockfile and manifest metadata; `detect-package-manager` published detection strategy details were **nothing found** in the accessible npm page ([npm, read 2026-10-22](https://www.npmjs.com/package/detect-package-manager)). Corepack reads the closest manifest's `packageManager`: “find the closest `package.json`” ([Node Corepack, read 2026-10-22](https://nodejs.org/download/release/v17.6.0/docs/api/corepack.html)).

**What this means for shotwright.** For `init` instructions, use explicit user choice if supplied, then package-local `packageManager` or lockfile, then the first user-agent token as a launch hint. Report ambiguity instead of silently preferring the repository-root lockfile. A subdirectory consumer needs commands for its own package.

## E. Node `require(esm)` and G13

- Node 22.12.0 release notes say `require(esm)` is “no longer behind a flag”; they say it was already default in v23.x. It still rejects an ES module graph with top-level await ([Node release, read 2026-10-22](https://nodejs.org/en/blog/release/v22.12.0): “ERR_REQUIRE_ASYNC_MODULE”). Node 20.19.0 release notes likewise say “no longer behind a flag” on v20 ([Node release, read 2026-10-22](https://nodejs.org/tr/blog/release/v20.19.0)). Node's versioned docs identify 23.0.0 as unflagged, and 23.5.0 as ending the warning by default ([Node v23 docs, read 2026-10-22](https://nodejs.org/download/release/v23.6.0/docs/api/modules.html): “v23.0.0 ... no longer behind”).
- Node points package authors to the `module-sync` export condition to route synchronous import and require to the same ESM ([Node 22.12 release, read 2026-10-22](https://nodejs.org/en/blog/release/v22.12.0): “`module-sync` exports condition”). An additional `require` condition is therefore not inherently needed for a synchronous ESM target; it would be appropriate only if shipping a separate CJS target or requiring distinct routing. This is an inference from Node's described condition.
- `arethetypeswrong` has an `esm-only` profile that ignores CJS resolution failures, and an open issue for `require(esm)` support ([CLI README](https://github.com/arethetypeswrong/arethetypeswrong.github.io/blob/main/packages/cli/README.md): “ignores CJS resolution failures”; [issue 253](https://github.com/arethetypeswrong/arethetypeswrong.github.io/issues/253), read 2026-10-22). A specific engines range endorsed by publint or arethetypeswrong for this case was **nothing found**. Thus `^20.19.0 || >=22.12.0` is a derived operational range for CJS `require(esm)`, not a quoted linter rule.

**What this means for shotwright.** If CommonJS config loading via `require(esm)` is a supported promise, raise the engine floor to the derived range and test it at 20.19 and 22.12. Avoid a `require` export pointing at the same ESM solely to imply a CJS build; verify the actual package export map and absence of top-level await.

## G. Non-image artifacts and G7

- `testInfo.attach(name, {body|path, contentType})` accepts a string/Buffer body or file path, exclusively; Playwright copies file attachments to a reporter-accessible location. Quote: “Either path or body must be specified, but not both” ([TestInfo, read 2026-10-22](https://playwright.dev/docs/api/class-testinfo)). It infers MIME type from path or defaults to `text/plain` for strings and `application/octet-stream` for buffers (same source, read 2026-10-22). `TestResult.attachments` exposes the same name, content type, path/body metadata ([TestResult, read 2026-10-22](https://playwright.dev/docs/api/class-testresult): “list of files or buffers”).
- The Playwright HTML reporter hosts attachments under `data/` and permits `attachmentsBaseURL` when files are uploaded elsewhere ([reporter docs, read 2026-10-22](https://playwright.dev/docs/test-reporters): “data folder to another location”). The Trace Viewer's Attachments tab lets a reviewer explore them ([Trace Viewer, read 2026-10-22](https://playwright.dev/docs/trace-viewer): “Attachments tab allows you to explore attachments”). A dedicated cross-harness “data artifact” vocabulary with normalization hooks for xlsx was **nothing found** in the targeted tools.

**What this means for shotwright.** Mirror the proven attachment input shape, but define independent storage, manifest MIME/size, filename safety, and text-versus-binary rendering. Treat xlsx normalization as an optional later extension; byte equality alone is not a semantic workbook comparison.

## G6 recommendation

**Yes: opt-in gating.** Always compute and show a pair state plus diff, and write `compare.json`; exit 1 for changed pairs only with `--fail-on-change`. Use the vocabulary **`identical`**, **`changed`**, **`size-changed`**, with `added`, `removed`, and `unreadable` for unpaired or invalid inputs. `identical` must mean zero differing decoded pixels under the chosen threshold, not a visual approval; include the threshold, differing count, ratio, image dimensions, and tool/version in the summary. For size changes, do not silently pad/crop and pronounce parity. The opt-in gate fits the project's artifact-review default while giving parity consumers an explicit assertion mode. This is a project recommendation based on the comparison results and approval separation above, not a claim that every surveyed tool defaults to a zero exit.
