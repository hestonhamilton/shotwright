# shotwright-2sr.6 — Research: uncommitted board data and backup verification

## Question

How should the only off-machine board backup prove that it retains Dolt working-set changes left by `bd remember` in shared-server mode? The bead correction is central: a dirty local `config` row was **measured**; its absence from the archive was **inferred**, never measured. Upstream links were read 2026-10-27. The disposable experiment and exact transcript are in `local/2sr.6-experiment/LOG.md` (relative to the repository root). No live-board or real-backup operation was performed in this revision.

## Context

**Measured (bead record, 2026-10-27):** On bd 1.1.0 and 1.3.2, `bd remember` left `kv.memory.*` rows in `config` WORKING. Manual `bd vc commit` cleaned the board. The research's earlier read-only `bd sql` inspection found a clean status after those commits; it did not prove the earlier backup lost rows.

**Read locally:** `scripts/backup-push.sh:113-171,188-235` takes source counts and HEAD, runs `bd backup sync`, clones the staged backup with `dolt clone file://...`, compares issue and commit counts, then copies the archive and manifest. It does not compare `config` content or WORKING status. `scripts/backup-verify.sh:151-190,243-272` checks known commit, counts, destination files, and freshness; it does not restore the destination archive. ADR 0016 requires a restorable content proof (`docs/adr/0016-off-machine-backup-is-rsync-over-ssh-of-a-proven-copy.md:38-49`), and ADR 0017 says this is the only off-machine copy (`docs/adr/0017-no-off-site-copy-of-the-board.md:25-28`).

## Findings

1. **Native sync retains the checked-out working set in this disposable Dolt version; clone omits it.** **Measured (2026-10-27, Dolt 2.2.1):** In `local/2sr.6-experiment/source/`, a `config` table had one committed row and one later uncommitted row; `dolt_status` reported `config,0,modified`. A disposable SQL server ran `DOLT_BACKUP('add',...)` and `DOLT_BACKUP('sync',...)`. After stopping it, `dolt backup restore` into `local/2sr.6-experiment/restored/` showed **both** rows and the same dirty status. Separately, `dolt clone` into `local/2sr.6-experiment/cloned/` showed **only the committed row** and empty status. The backup data is in `local/2sr.6-experiment/backup/`; exact commands, outputs, two failed client setup attempts, and process cleanup are logged in `local/2sr.6-experiment/LOG.md`. The optional non-current-branch working-set repeat was skipped. **Read upstream:** Dolt says backup sync includes working sets and demonstrates restoring an uncommitted insert ([backup CLI](https://www.dolthub.com/docs/cli-reference/cli/), [server backup guide](https://www.dolthub.com/docs/sql-reference/server/backups/), read 2026-10-27). **Inferred:** the existing clone/count proof is a committed-board floor, not evidence about working sets. This experiment does not establish the contents of the script's actual staged or off-machine archive, nor every Dolt/bd version or branch working set.

2. **The actual bd backup path has a precommit, with a `config` gap.** **Read upstream:** Direct v1.3.2 `bd backup sync` calls `store.Commit(ctx, "bd: pre-backup commit")`, warns and continues on failure, then calls `BackupSync` ([backup_dolt.go:171-180](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/backup_dolt.go#L171-L180), [versioncontrolops/backup.go:24-29](https://github.com/gastownhall/beads/blob/v1.3.2/internal/storage/versioncontrolops/backup.go#L24-L29), read 2026-10-27). `DoltStore.Commit` excludes `config`, so that precommit cannot settle a config-only memory row ([store.go:3343-3355](https://github.com/gastownhall/beads/blob/v1.3.2/internal/storage/dolt/store.go#L3343-L3355), read 2026-10-27). The proxied path calls `DOLT_COMMIT('-Am')` before `DOLT_BACKUP` and has a comment saying backup sync is committed-history-only ([backup_proxied_server.go:196-250](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/backup_proxied_server.go#L196-L250), read 2026-10-27). **Inferred:** the comment is an upstream assumption that conflicts with Dolt's documented semantics, not proof of omitted working sets. The experiment mirrors the server `DOLT_BACKUP` calls but did not run bd's precommit or its proxied path. A plan pin must test the staged artifact made by the actual script, including the config-only precommit case and any ignored precommit failure.

3. **The memory producer gap still exists in v1.3.2.** **Read upstream:** Direct `remember` writes `kv.memory.*` in SQL, marks a post-command write, and the v1.3.2 epilogue returns outside embedded mode ([memory.go](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/memory.go), [memoryops/memories.go](https://github.com/gastownhall/beads/blob/v1.3.2/internal/storage/memoryops/memories.go), [dolt_autocommit.go:132-166](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/dolt_autocommit.go#L132-L166), read 2026-10-27). `dolt.auto-commit=on` is already the normal default ([main.go:1833-1844](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/main.go#L1833-L1844), read 2026-10-27). [PR #7608](https://github.com/gastownhall/beads/pull/7608) closed [#4078](https://github.com/gastownhall/beads/issues/4078) on the main branch before v1.3.2's 2026-10-24 release, but the tag was cut from `hotfix/1.3.1`. The [tag-versus-merge comparison](https://github.com/gastownhall/beads/compare/v1.3.2...8d2b4152f73042a37df4e6269e22074c8f910bbd) diverges, the [tagged epilogue](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/dolt_autocommit.go#L141-L145) still returns in server mode, and the [tagged changelog](https://github.com/gastownhall/beads/blob/v1.3.2/CHANGELOG.md) omits #7608 (all read 2026-10-27). **Measured (bead record):** bd 1.3.2 reproduced the dirty memory row. [#4383](https://github.com/gastownhall/beads/pull/4383) is a separate open proposal, not evidence that #7608 shipped (read 2026-10-27).

4. **Archive content and current local status answer different questions.** **Inferred; redteam finding 5 is bead-worthy:** A dirty local status after a successful backup can be a useful operational warning, but it does not show that the archive omitted the row. For example, a later local memory write could trigger a false alarm against a healthy prior archive. Likewise, a clean local status after a row was committed or reset could give false green for an older archive that omitted it. A claim about the staged archive needs a disposable `backup restore` plus snapshot-specific `config` row and status inspection; a claim about the off-machine copy needs at least one destination readback/restore check. Preserve the existing clone/count result as the committed-board floor. Report a dirty local board separately, without suppressing a verified fresh copy solely for being dirty. The [Dolt working-set guide](https://www.dolthub.com/docs/concepts/dolt/git/working-set/) defines WORKING separately from commits (read 2026-10-27).

5. **An explicit commit is a real owner policy option.** **Read upstream:** v1.3.2 `CommitAll`, used by `bd vc commit`/`bd dolt commit`, stages `config` and other committable pending tables ([store.go:3610-3651](https://github.com/gastownhall/beads/blob/v1.3.2/internal/storage/dolt/store.go#L3610-L3651), read 2026-10-27). **Measured (bead record):** manual `bd vc commit` cleaned this board. **Inferred:** a timer could run an attributable `bd vc commit`, check status and HEAD, then back up; that repairs the observed producer gap with a small operational change. It also publishes unrelated pending batch changes or a concurrent writer's completed SQL transaction under the backup job's message. The shared workspace gate does not serialize ordinary writers ([workspace_gate.go](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/workspace_gate.go#L18-L24), read 2026-10-27). This tradeoff belongs to the owner; an exclusive lock is not established as a prerequisite by the current evidence.

## Options with risks

| Option | Benefit | Risk / condition |
| --- | --- | --- |
| **D. Restore and inspect native backup — recommended** | Proves the staged archive includes the relevant WORKING row and status, while retaining a fresh off-machine copy. Matches the disposable result and Dolt's documented backup contract. | The experiment did not test the actual staged or destination copy. Design a snapshot-specific row/status comparison, then read back and restore the destination before claiming off-machine coverage. Keep dirty local status as a separate warning. |
| A. Explicit `bd vc commit` before sync | Small producer repair: `CommitAll` includes `config`; HEAD and clean status can be checked before backup. | Publishes all pending committable changes with a backup-job message. The owner must choose whether this is acceptable, especially with batch mode and concurrent writers. Backup content still needs independent proof. |
| B. Fail push on any dirty WORKING | Enforces a committed-only operational contract if the owner explicitly chooses one. | Can age out the only off-machine copy even when native backup retains the row. Dirty status alone is not evidence of content loss; fail on a failed content proof instead. |
| C. Upgrade bd or change auto-commit policy | A future released producer fix may reduce dirty states. | v1.3.2 still has the gap and already defaults to `on`; a version-pinned reproducer and archive proof remain necessary. |

## Recommendation

**Inferred from the measured experiment:** carry option **D** into P. The proof should restore a disposable copy of the actual staged archive, inspect its `config` WORKING row and `dolt_status` against a snapshot-specific source observation, then verify a readback of the off-machine archive before reporting that working-set coverage is green. Continue to report the existing clone/count result only as a committed-board floor. If the content proof fails, fail the push and investigate the exact version/path; do not fail a verified push merely because local status is dirty. The verifier should describe archive content and freshness separately from a current-local-dirty warning. Test an ignored bd precommit failure and source changes during sync as concrete remaining risks in P.

The owner can instead choose an explicit `bd vc commit` before sync, with its publication semantics stated plainly. The current evidence does not justify a new exclusive lock spanning backup or a broad status framework. Redteam findings 7 and 8 are **declined**: the wider lock/write-path expansion is outside this bead's proven need, and this research document has no headed-public leak. The adjacent hardcoded scratch example in `docs/backup.md` is outside this document's edit scope.

## Open questions for the owner

1. Should the scheduled job preserve intentionally uncommitted WORKING rows, as option D proposes, or first publish all pending committable rows with an attributable `bd vc commit`?
2. What archive-specific row or identity should the P proof use for a config-only memory change without exposing its value in logs? The choice must let restore results be matched to the staged snapshot and destination readback.
