# shotwright-2sr.5 — Research: shared-server backup destination collision

Read date for all linked upstream material: **2026-10-27**. Evidence labels below mean **measured locally** (read-only inspection), **read upstream** (linked source, issue, or release), or **inferred** (a conclusion that has not been reproduced as a new write). No server or board state was changed for this research.

## Question

How did `beads_global` acquire shotwright's automatic Dolt backup destination, and what supported, database-scoped repair will keep it from writing there? The incident is recorded in `bd show shotwright-2sr.5`, `docs/backup.md`, and ADRs 0016–0017. **Measured locally:** this is still a live registration collision: `bd --global sql 'SELECT name, url FROM dolt_backups'` shows `backup_export` aimed at shotwright's `.beads/backup`; the shotwright query shows the same `backup_export` plus a distinct manual `default` destination under `~/.local/state/beads-backup/shotwright`. The premise that shotwright's *only* registered backup is `.beads/backup` is now stale. The off-machine script uses a separately restored and counted manual backup; it does not read `.beads/backup` (`docs/backup.md`, ADR 0016). ADR 0017 accepts one off-machine copy and no off-site copy.

## Findings

### 1. Destination selection and registration in bd 1.1.0

**Read upstream:** Auto backup is enabled by default when a git remote exists, unless `backup.enabled` is explicit; the post-command path calls `backupDir()`, checks a state file and throttle, then invokes `runBackupExport()` ([`cmd/bd/backup_auto.go:15-23,62-138` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_auto.go#L15-L138), read 2026-10-27). `backupDir()` chooses `backup/` inside `backup.git-repo` when valid, otherwise `<current workspace>/.beads/backup`; it creates that directory ([`cmd/bd/backup_export.go:24-53` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_export.go#L24-L53), read 2026-10-27). `runBackupExport()` hands that directory to the active store and writes `backup_state.json` **in the directory**, with no database identifier in the state path ([`cmd/bd/backup_export.go:114-156` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_export.go#L114-L156), read 2026-10-27).

**Read upstream:** `BackupDatabase` converts that directory to `file://`, removes any old `backup_export` registration on the connected database, adds the same name with the chosen URL, then syncs it. The remove error is ignored; an address conflict with another name *on that database* causes a sync through that name ([`internal/storage/dolt/store.go:771-805` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/internal/storage/dolt/store.go#L771-L805), read 2026-10-27). The helper issues `CALL DOLT_BACKUP('add'|'sync'|'rm', ...)` on the store's SQL connection ([`internal/storage/versioncontrolops/backup.go:10-31` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/internal/storage/versioncontrolops/backup.go#L10-L31), read 2026-10-27). **Inferred:** Dolt's address-conflict handling here cannot detect another database's destination, so two databases can independently register one filesystem URL.

**Read upstream:** `--global` changes the connected database to `beads_global` but does not change workspace discovery ([`cmd/bd/main.go:1089-1096` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/main.go#L1089-L1096), read 2026-10-27). **Inferred:** a `bd --global` command run from shotwright while auto backup was due could register `beads_global` against shotwright's workspace directory. This explains the observed URL; the exact historical command and time of first registration are **not known**. A different project or explicit `backup.git-repo` could have produced a similar mismatch. The draft report's claim that this happened simply because the *first* command touched `beads_global` is too strong: the code requires auto backup to be enabled and due, with a changed commit.

**Read upstream:** `bd backup init <path>` is a separate manual path: it registers the name `default` and saves metadata in the current workspace's `.beads/dolt-backup.json` ([`cmd/bd/backup_dolt.go:56-96,216-246` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_dolt.go#L56-L96), read 2026-10-27). It does not choose the automatic `backup_export` directory. **Measured locally:** shotwright currently has both names; `beads_global` has only `backup_export`.

### 2. Prior reports, changes, and release currency

**Read upstream:** The latest stable GitHub release on 2026-10-27 is **v1.3.2**, released 2026-10-24 ([release](https://github.com/gastownhall/beads/releases/tag/v1.3.2), read 2026-10-27). The v1.3.0 changelog says auto backup now defaults **off** in server, shared-server, and proxied-server modes; an explicit `backup.enabled` or `BD_BACKUP_ENABLED` still overrides it ([`CHANGELOG.md:1278-1288` at v1.3.2](https://github.com/gastownhall/beads/blob/v1.3.2/CHANGELOG.md#L1278-L1288), read 2026-10-27). v1.3.2 source confirms that default ([`cmd/bd/backup_auto.go:19-42`](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/backup_auto.go#L19-L42), read 2026-10-27). **Inferred:** upgrading would stop *default-driven* re-registration from shared-server commands, but would neither erase this existing `backup_export` entry nor prevent collision after an explicit opt-in. Upgrading from 1.1.0 is a schema and fleet change, not a binary-only repair: read the [upstream shared-server upgrade procedure](https://github.com/gastownhall/beads/blob/v1.3.2/docs/getting-started/upgrading.md#shared-servers) (read 2026-10-27) before considering it.

**Read upstream:** v1.3.2 still resolves auto backup from the workspace's directory and registers fixed-name `backup_export` through remove/add/sync ([`cmd/bd/backup_export.go:28-53`](https://github.com/gastownhall/beads/blob/v1.3.2/cmd/bd/backup_export.go#L28-L53), [`internal/storage/versioncontrolops/backup.go:65-103`](https://github.com/gastownhall/beads/blob/v1.3.2/internal/storage/versioncontrolops/backup.go#L65-L103), read 2026-10-27). It fixes a different auto-backup watermark race, not cross-database destination identity ([v1.3.2 release notes](https://github.com/gastownhall/beads/releases/tag/v1.3.2), read 2026-10-27). **Inferred:** the collision remains possible when server-mode auto backup is explicitly enabled.

**Read upstream:** [Issue #2962](https://github.com/gastownhall/beads/issues/2962) and merged [PR #2980](https://github.com/gastownhall/beads/pull/2980) address `backup_export` versus `default` **within one database**, not two databases sharing a destination (read 2026-10-27). [Issue #3594](https://github.com/gastownhall/beads/issues/3594) concerns a client filesystem path sent to a remote server; it is related to location selection but not this local shared-server collision (read 2026-10-27). [Issue #2993](https://github.com/gastownhall/beads/issues/2993) proposes a broader backup redesign (read 2026-10-27). **Inferred from searches of upstream issues, PRs, discussions, and the release changelog on 2026-10-27:** no exact report or fix for a `beads_global`/project destination collision, or for status accepting the wrong database's content, was found. This is a search result, not proof that none exists.

### 3. Database-scoped remediation without raw `dolt`

**Read upstream:** `bd backup remove` first tries to remove `default`; if that fails, it returns `no backup destination configured` **before** attempting `backup_export` ([`cmd/bd/backup_dolt.go:397-447` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_dolt.go#L397-L447), read 2026-10-27). **Measured locally:** `beads_global` has no `default`. Therefore `bd --global backup remove` is **not** a supported way to remove this registration on this installation. `bd --global backup init <dedicated-path>` would add or update `default` but leave `backup_export` pointing at shotwright; the next auto backup would still use the workspace path ([`cmd/bd/backup_dolt.go:56-96`](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_dolt.go#L56-L96), [`cmd/bd/backup_export.go:114-142`](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_export.go#L114-L142), read 2026-10-27).

**Read upstream:** The supported Dolt SQL procedure is `CALL DOLT_BACKUP('rm', 'backup_export')`, and `bd sql` passes SQL to the connected database ([`internal/storage/versioncontrolops/backup.go:26-31` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/internal/storage/versioncontrolops/backup.go#L26-L31), read 2026-10-27; `bd sql --help`, measured locally). The exact **proposed, not executed** database-scoped command is `BD_BACKUP_ENABLED=0 bd --global sql "CALL DOLT_BACKUP('rm', 'backup_export')"`. The environment override disables an immediate post-command auto backup; it must also be used on subsequent global commands until a durable policy is in place ([`internal/config/config.go:399-416` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/internal/config/config.go#L399-L416), [`cmd/bd/backup_auto.go:15-23` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_auto.go#L15-L23), read 2026-10-27). `--global` selects `beads_global` ([`cmd/bd/main.go:1089-1096` at v1.1.0](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/main.go#L1089-L1096), read 2026-10-27). **Measured locally:** `bd --global sql 'SELECT name, url FROM dolt_backups'` returns one row, while the same query without `--global` returns two; this is a usable before/after check without touching shotwright's registration. Also read `<shared-server>/dolt/beads_global/.dolt/repo_state.json` and the shotwright counterpart to compare URLs. **Inferred:** the removal is temporary under 1.1.0 if any later global command from this or another project triggers auto backup; it will recreate `backup_export` from that command's workspace. Preventing re-registration requires disabling auto backup for every relevant 1.1.0 client that uses `--global`, or upgrading all clients to the server-mode default-off behavior and checking explicit overrides. Neither is an isolated one-database setting in the inspected 1.1.0 path.

**Read upstream:** `bd backup status` reads workspace-local `backup_state.json` and `.beads/dolt-backup.json`; it does not inspect the registered destination's contents or compare database identities ([`cmd/bd/backup.go:47-113`](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup.go#L47-L113), [`cmd/bd/backup_dolt.go:303-348`](https://github.com/gastownhall/beads/blob/v1.1.0/cmd/bd/backup_dolt.go#L303-L348), read 2026-10-27). **Measured locally:** `bd backup status --global` and `bd backup status` printed identical shotwright timestamps and manual destination, despite distinct `dolt_backups` rows. Therefore verification must use `bd --global sql 'SELECT name, url FROM dolt_backups'`, the shotwright query, and a restore/content check for any destination intended to be trusted. `bd backup status` alone cannot verify this fix.

### 4. Risk to shotwright and other projects

**Inferred from the database-scoped SQL and local registrations:** removing `beads_global.backup_export` leaves the shotwright database's `backup_export` and `default` registrations untouched. It also leaves backup files on disk; it does not delete the shared destination. A mistaken omission of `--global` would remove shotwright's `backup_export`, which its next eligible auto backup could recreate; that would affect a local untrusted copy, not `scripts/backup-push.sh`. A mistyped SQL name or database selector is the principal immediate operational risk. **Measured locally:** other project databases have not been inspected in this research, so their registration state is unknown. **Inferred:** changing a machine-wide auto-backup setting or upgrading the shared client fleet may alter their backups and schema compatibility; inspect each project's policy before either change.

## Recommendation

**Inferred:** file the corrected upstream report as a distinct issue, citing #2962, #2993, and #3594. For local remediation, first inventory explicit `backup.enabled` settings and all clients that use `--global`; arrange for global auto backup to stay off. Then, in an authorized later phase, run only the scoped `BD_BACKUP_ENABLED=0 bd --global sql "CALL DOLT_BACKUP('rm', 'backup_export')"`, query both databases' `dolt_backups` tables, and confirm a subsequent global write does not recreate it. Continue to trust only the restore-proven off-machine path in `docs/backup.md`. Treat a v1.3.2 upgrade as a separate fleet migration, not as a prerequisite for reporting or a standalone collision repair. No write or upstream post was made in this research phase.

## Redteam outcome (2026-10-27)

A fresh redteam re-opened every citation and re-measured both `dolt_backups` tables read-only. The mechanism, the `bd backup remove` early return, the v1.3.0 default-off change, v1.3.2 being the latest release, and the local registrations all held. No fix-now finding. Carried into the plan:

1. **Sequencing is overtaken.** The owner has since directed a machine-wide bd upgrade, so the Recommendation's "separate later migration" no longer applies. The plan sequences upgrade, then removal, then verification. The [shared-server upgrade guide](https://github.com/gastownhall/beads/blob/v1.3.2/docs/getting-started/upgrading.md#L327-L375) requires explicit consent for each database's migration (`--global` for `beads_global`), and the [v1.3.2 release notes](https://github.com/gastownhall/beads/releases/tag/v1.3.2) carry migration 0059 and backup-recovery cautions (read 2026-10-27).
2. **Missed prior art for the false-status half of the upstream report:** [#5209](https://github.com/gastownhall/beads/issues/5209) (a live `backup_export` shown as `configured: false`) and [#5742](https://github.com/gastownhall/beads/issues/5742) (contradictory enabled/freshness output). For concurrent re-registration: [#3878](https://github.com/gastownhall/beads/issues/3878) and [PR #3869](https://github.com/gastownhall/beads/pull/3869). Read 2026-10-27. Still no exact duplicate.
3. **One global write after removal is too weak a persistence check.** Re-check after every relevant client has run on the upgraded fleet, with the version and `backup.enabled`/`BD_BACKUP_ENABLED` inventory in hand.
4. **A missing registration row is not a trustworthy backup.** [#4070](https://github.com/gastownhall/beads/issues/4070) records a manifest that got ahead of missing chunks. `scripts/backup-verify.sh` remains the only trust gate for shotwright.
5. **Operator selection is the main risk of the SQL removal.** Pin the connection with `SELECT DATABASE()` and the exact `dolt_backups` rows in the same environment immediately before and after the write. Omitting `--global` removes shotwright's `backup_export` instead.
